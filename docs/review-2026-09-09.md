# Engineering review — 9 September 2026

Robustness and architecture review of the v2 foundation.

**Scope note, stated honestly:** this is a young codebase — ~2,500 lines including
markup, built over a handful of sessions. It is not production-scale, and framing
it as such would flatter it. The review standard still applies, and the defects
below are real, reproduced, and were found by looking rather than by assuming.

## Findings

### 1. Arbitrary file write via upload path traversal — CRITICAL

`upload_source` joined the raw multipart filename onto the project directory:

```python
(project.sources_dir / upload.filename).write_bytes(content)
```

**Reproduced before fixing.** A filename of `../../../ESCAPED.txt` resolved to the
repository root, outside the project entirely. The multipart filename is fully
attacker-controlled.

**Fixed** by introducing [sources.py](../src/pipeline/sources.py) as the single
owner of "may this file enter a project?". Filenames are reduced to a bare name
under both POSIX and Windows conventions, sanitised, then the resolved destination
is re-checked against the target directory — belt and braces, because sanitisation
alone is one refactor away from being wrong.

**Verified:** 7 traversal payloads as unit tests, plus an end-to-end test through
the real HTTP route asserting no file appears outside the project. Also confirmed
manually against the running server.

### 2. Unbounded, untyped uploads

No size limit (content read fully into memory), no type check despite the UI
advertising PDF/MD/TXT/DOCX/PPTX, no empty-file check.

An empty file passes every downstream stage and fails inside extraction, where the
cause is no longer visible.

**Fixed:** 64 MB cap, suffix allow-list, empty-file rejection — all before any
write. Rejection messages name what *is* allowed, not just what was refused.

### 3. Upload was all-or-nothing

One bad file in a batch produced a 500 with no indication which file failed.

**Fixed:** each file is validated and written independently; the response carries
`accepted` and `rejected` lists with a per-file reason. Renames are reported too —
a silently renamed file is a small betrayal.

### 4. Blank page on any first-load failure — HIGH

`boot()` had no error handling. If `/api/stages` failed — server down, network
blip — the promise rejected into nothing: **no error, no retry, no indication
anything had happened.** The worst failure mode on the list: silent, invisible,
undiagnosable.

**Fixed:** loading state, caught failure, visible message, retry button.

### 5. Silent data loss on a failed write — HIGH

A page made five raw `fetch` calls and checked `response.ok` on none. The POST was
the dangerous one: on failure the UI advanced **exactly as it did on success**, so
a lost write was indistinguishable from a saved one.

**Fixed at the cause.** Two pages had two different HTTP conventions and neither
was shared. Extracted
[shared-client.js](../src/pipeline/web/static/shared-client.js) — one definition of
how HTTP failure behaves. Local state now updates only after the server confirms.

### 6. HTML escaping missed quotes

`esc()` escaped `& < >` but not `"` or `'`, and its output was interpolated into
HTML attributes. Not currently exploitable — every interpolated value happened to
be server-sanitised — but safe *by accident*, which is not a property to rely on.

Two independent copies existed, both wrong.

**Fixed:** one `escapeHtml` in the shared module, covering all five characters.

### 7. Check-then-create race in `ProjectStore.create`

`if d.exists()` then `mkdir` is a TOCTOU window. The loser of a concurrent create
raised a raw `FileExistsError` — surfacing as a 500 rather than the intended 400.

Worse, a failure *after* the directories were made left a half-built project:
invisible to `list()` (no metadata) but blocking `create()` (directory exists). A
wedged slug with no recovery from the UI.

**Fixed:** `mkdir(exist_ok=False)` makes the filesystem the arbiter; the error is
translated to `ValueError`; any failure removes the partial directory.

### 8. Inconsistent durability for the same concern

`Manifest.save` wrote atomically via temp-file-and-rename. `ProjectStore` wrote
`project.json` directly. Same codebase, same concern, two standards — and the
weaker one is what gets copied into the next module.

**Fixed:** both now write atomically, with the reasoning recorded where a reader
will find it.

### 9. Corrupt project metadata failed silently

`_load` swallowed `JSONDecodeError` and returned `None`, so a project with a
corrupt `project.json` **disappeared from the UI with no signal**. That reads to a
user as "it deleted my work."

**Fixed:** still hidden — it genuinely cannot be read — but logged at ERROR naming
the project and the reason. A `null` metadata object is also caught now. Stray
directories without metadata stay silent, because those are not errors.

### 10. Duplicated definition of "supported file type"

`projects.py` had its own `SOURCE_SUFFIXES` set; `sources.py` had another. Two
answers to one question is how the API and the UI end up disagreeing about which
files are acceptable.

**Fixed:** one definition, re-exported.

### 11. A docstring that contradicted its own code

A service docstring claimed it was "held as a singleton via DI rather than a
module global" while sitting directly above a module global.

**Fixed:** the docstring now describes what the code actually does, including the
consequence that matters — a test changing settings must reset the cache.

## Deliberately not fixed

### No authentication

The app binds to `127.0.0.1` and assumes one trusted local operator. No auth, no
CSRF, no rate limiting.

Adding auth now would be premature: who operates this is
[Q4](open-questions.md#q4--who-operates-this), still open, and the answer decides
whether this is a local tool or a hosted product. **Recorded as an explicit
assumption in [system-map.md](architecture/system-map.md)** with the four things
that need revisiting if it ever leaves localhost.

### `slugify` has no length cap

A 300-character project name produces a 300-character directory name. Combined
with nested chapter paths on Windows this could approach `MAX_PATH`.

Not hit in practice, and a cap changes the slug of any existing long-named project.
Recorded in the known-gaps table rather than fixed silently.

## What I did not verify

Stated plainly rather than implied:

- **No browser testing.** Page rendering, keyboard navigation, focus states,
  responsive behaviour and mobile layout were not exercised in a real browser. The
  JS changes were verified by serving and by static reading only.
- **No concurrency testing.** The TOCTOU fix is argued from the code, not proven
  under simultaneous requests.
- **No load or large-file testing.** The 64 MB limit is enforced, but behaviour
  near it was not measured.
- **Stage execution does not exist**, so nothing about the pipeline's actual
  behaviour was tested — only the surface around it.

## Remaining risks

1. **Uploads are read fully into memory.** The 64 MB cap bounds this, but several
   concurrent large uploads still multiply. Streaming to disk would be the real
   fix.
2. **No request-size limit at the ASGI layer.** Validation happens after the body
   is read.
3. **`stale` state is designed and tested but unwired** — the manifest is built
   and nothing writes to it. A reader could reasonably assume incremental rebuild
   works today. Called out in the system map for exactly that reason.
4. **Frontend has no automated tests.** All 56 are Python. The JS contract is
   enforced by convention and review, not by CI.

## Character preserved

The review did not flatten the UI to make it robust.

- The **five stage colours** remain, and now drive more than the tab: heading,
  card accents, notice borders and primary buttons all inherit the active stage's
  colour, so each stage reads as its own place.
- Feedback gained a **notice line per stage** rather than `alert()` — failures
  appear where the user is already looking, in the stage's own colour for success
  and a distinct red for failure.
- Disabled buttons now say why they are disabled (`Saving…`) rather than going
  inert silently.

## Where a feature belongs now

The review asked whether adding a feature has an obvious home. It does:

| Concern | Home |
|---|---|
| A new stage | `stages.py` — one entry; tabs and API follow automatically |
| A new agent capability | `tools.py`, then declare it in the stage's `AGENT.md` |
| A new external asset source | `tools.py` `RESOURCES`, with its licence |
| New input validation | `sources.py` — the only admission gate |
| A new path | `storage/layout.py` — no string concatenation elsewhere |
| A new API route | `web/routes_project.py`, thin, delegating to a domain module |
| New browser HTTP | `requestJsonFromApi` — never a raw `fetch` |
